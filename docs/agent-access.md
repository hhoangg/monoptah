# Agent access with /operator

## Enable access

Type `/operator` at the start of a composer message to enable Monoptah access in that thread. For example, `/operator start two Codex sessions: one to inspect the API and one to review the UI`, or `/operator list my notes`. The slash picker also offers this command. The transcript shows only the request text in a translucent amber bubble; Monoptah removes the command from the request sent to the agent and supplies the local `app` CLI path and instructions on that turn. Later turns in the same thread can use the CLI without repeating `/operator`; other threads receive no CLI instructions or app access. The CLI can act only during an active agent turn. The agent can run the shown `app --help` command for the exact JSON input fields.

## CLI actions

Sessions started by an ordinary Operator remain visible in project history.
Monos use the same project actions, with their **Show started sessions** setting
controlling whether their launches appear in the user's history. This is
independent of navigation: `reveal` defaults to `false`, so a background launch
can stay visible in history without switching the user's current conversation.

- `models.list` shows available providers, models, settings, and permission modes.
- `sessions.start` creates a session in the current project with a prompt. Set `reveal: true` to open its tab, or `placement: "right"` / `placement: "down"` to split the calling session's pane; `besideSessionId` selects another visible session pane in the project. Reuse the returned session ID as the next `besideSessionId` to build nested layouts. By default it submits the prompt; set `draft: true` to save it unsent without starting an agent turn. It accepts a provider, model, effort or other model settings, permission mode, and current checkout or new worktree choice. Set `worktreeCwd` to a path from `worktrees.list` for a specific existing checkout. Use `worktrees.create` to create a worktree on a named new or existing local branch, then pass its path as `worktreeCwd`. Omit `runtimeMode` to inherit the calling session's permission mode, or set it explicitly to override. It returns the new session ID as soon as the pane and prompt are accepted, so the agent can move it into a folder immediately.
- `sessions.start` accepts `account` (a Mono only; an Operator is refused): the label, id or `default` of a provider account of the session's harness, so the session runs with that account's sign-in. Matching is exact (id, or label ignoring case and extra spaces), never by prefix. An unknown, ambiguous or other-provider name is an error that lists the valid labels and ids. It applies to local sessions only: with a cloud `target` it fails with "account applies to local sessions only", because a cloud session uses the cloud setup. Without `account`, the session uses the account set in the Mono's settings under **Sessions it starts** when it runs on that settings' provider (which may differ from the Mono's own, with its own model and effort), else it inherits the Mono's account for the same provider, else the project's choice or the provider's default account. A request that names `harness`, `model`, `modelSettings` or `effort` keeps its own choice and is never given the settings' provider, model or effort; an explicit `account` always wins, and a cloud `target` ignores the settings' account. If the account in the settings no longer exists, the call fails with an error that says so. When a session stops on a usage limit, its completion report names the provider and account label (never a token or email). Models are validated against the chosen account.
- `sessions.moveToCloud`, `sessions.moveToLocal`, `sessions.moveStatus` and `sessions.cancelMove` (a Mono only; an Operator is refused) move a conversation between this computer and a codespace or Docker sandbox, exactly as the app's **Continue in cloud** and **Continue locally** do. `sessions.moveToCloud {session, target: {kind: "codespace" | "sandbox", instance: "new" | "<name>"}, kit?: "none" | "default", project?}` can only narrow the user's choices: the branch is pushed without force and never to the default branch (a diverged or default branch goes to `<branch>-cloud`), uncommitted changes travel as a patch over the tunnel and are never pushed, and ignored files such as `.env` are never uploaded. `instance: "new"` needs a GitHub repository (codespace) or the project's saved sandbox setup; a name must already run a session of the project. `kit: "none"` sends no Claude setup to the new workspace, `"default"` follows the user's Settings and adds nothing. Any other key (`force`, `deleteBranch`, `deleteWorkspace`, `skipChecks`, kit items) is refused, and a refused call creates nothing. The call returns at once (`state: "running"`); the move runs in the app as a normal move that the user can follow and cancel, marked "Started by an agent". `sessions.moveToLocal {session, project?}` only opens the Continue locally confirmation (`state: "awaitingConfirmation"`); nothing runs until the user presses Continue, and it is refused while a turn runs here. A session born in the cloud comes back under a new id: `sessions.moveStatus` on the old id then answers `state: "done"` with `newSession`. The move actions are never available to a habit run, heartbeat or workflow question, nor for the caller's own chat, another Mono's chat or a worker session. A move an agent starts shows a notice and "Started by an agent" in the conversation banner and dialog. `sessions.moveStatus {session, project?}` reads the move without waking anything (steps, the push branch, notes, the error with filesystem paths replaced by `<path>`; no account or secret). `sessions.cancelMove {session, project?}` is the dialog's Cancel for a move an agent started (a move the user started is the user's to cancel): it never deletes a workspace or a pushed branch.
- `accounts.list` (Monos and Operators, read only) takes an optional `provider` (`claude`, `codex` or `devin`) and returns `{accounts:[{provider,id,label,isDefault,authKind}]}`, where `authKind` is `cli`, `setupToken` or `apiKey`. It never returns a token, email or path.
- `sessions.start` and `sessions.send` accept `completionDelivery: "group" | "each"` (default `"group"`). With `"each"`, the session's completion report reaches the calling Mono as soon as that session stops, without waiting for the Mono's turn or sibling sessions, as a new turn once the Mono is idle (several may queue while it is busy). Habit runs always use `"each"`: sessions a habit run starts report to the Mono's chat, not to the run, and the report still arrives after the run has ended. The field is ignored when the launch is not monitored (a draft, or `notifyOnComplete: false`).
- `sessions.start` accepts `parentSessionId` from a Mono or its habit runs. The new session is nested under that parent in the sidebar and its ID becomes `app-<parentSessionId>-<requestId>`. The parent must be a session that Mono (or its habit runs) started in the same project during the current app run; the record is kept in memory and lost on restart. Nesting is one level deep, so a child cannot be a parent. IDs over 255 characters are rejected, so use a short request ID. The completion report still goes to the Mono, and the child gets no app access.
- `sessions.start` accepts `folderName` (up to 100 characters) and `folderId` to file the new session in a folder. An existing `folderId` wins and the folder is never renamed. An unknown `folderId` with a `folderName` creates a new folder; an unknown `folderId` alone fails with "Folder was not found in this project". A `folderName` alone always creates a new folder, even if one with that name exists. New folders use the Mono's color, and the result includes `folderId` and `folderName`. Without these fields the session goes in the Mono's default folder when **Group in a folder** is on for that Mono.
- `parentSessionId`, `folderName` and `folderId` do not override a Mono's hidden-launches setting. For them to show, turn on **Show sessions in sidebar** for that Mono; nesting is only drawn in the inset sidebar layout. Use request IDs without hyphens with `parentSessionId` so the sidebar cannot mistake another session's ID for the parent.
- `sessions.list` shows project sessions and their archived status. `sessions.read` returns up to three recent user/assistant exchanges, with a cursor for older exchanges and a per-message character cap. `sessions.send` submits a follow-up to an idle session, while `sessions.draft` saves an unsent message for the user to review. `folders.list` and `folders.move` organize project sessions in sidebar folders, including a new folder.
- `terminals.*` lets a Mono drive labeled terminals of its project, for example BE and FE side by side in one split view, and lets an ordinary coding session read them. Terminals are not saved: after a restart every terminal a Mono opened is gone (dock tabs, title tabs and panes alike), nothing is restored and there is no "Run again" bar; the user's own terminals come back as before. Ids are opaque (`t-<4 hex digits>-<n>`, the first part random per launch), belong to the running app and name nothing after a restart. Remote projects and cloud sandboxes are not supported, and habit runs, heartbeats and workflow questions cannot use `terminals.*`.
  - **Who may do what.** A Mono has `list`, `open`, `send`, `read`, `stop`, `close` and `layout`. A plain coding session (Operator need not be enabled; local sessions only, never `remote://` or cloud) has `terminals.list` and `terminals.read` and nothing else: every other `terminals.*` action answers `Only a Mono can open or drive terminals`. A session sees only the terminals whose folder (the live folder of the process holding the terminal when the system can tell it, else the folder it started in) is inside its own project or its worktree (`settings.worktree_cwd`); a terminal in another worktree or outside both is not listed and its id is unknown. It may pass `project` only if it is its own. Its answers are the same as a Mono's, with the same caps and masking.
  - **Reading.** `terminals.list {project?}` returns `[{id,label,cwd,place,running,exited,exitCode,owner}]` for every terminal of the project: the ones the Mono opened and the ones the user opened (`owner` is `mono` or `user`; another Mono's are not shown to a Mono). There is no per-terminal switch. Terminals that are not plain shells (a TUI agent session, a login, a cloud shell, `FixTerminal`, a terminal started with secret environment variables) and shells that are running an agent CLI are never listed and cannot be read. `terminals.read {id,lines?}` returns `{text,truncated,running,exited,exitCode}` with the last `lines` lines (default 200, at most 1000, 32 KiB); secrets are masked over the whole scrollback before it is cut, and a private key whose end is missing is masked to the end of the text.
  - **Opening.** `terminals.open {label,action?,command?,cwd?,place?,beside?,direction?,reveal?,project?}` opens a terminal named `label` (up to 40 characters, no control, zero-width or direction-changing character) and returns `{id,reused,place}` (`revealed:false` is added when `reveal` could not show it). `action` is the ID of a Project Action the user saved. `command` is a free shell command (give `action` or `command`, not both); it is typed and Enter is pressed at once. Without either the terminal is a plain shell. Terminals a Mono opens are ordinary shells with the user's normal history; nothing is changed about the shell's startup. `cwd` must be inside the project or one of its git worktrees (`..` is refused, symlinks are resolved). `place` is one of `dock` (a tab of the project's dock), `tab` (a title tab of its own, not a split and not part of the Logs tab) or `split` (a pane beside the terminal in `beside`, else in the Mono's Logs tab of the project, else in a title tab of its own that becomes that Logs tab; the user's chat tabs are never split), with `direction` `right` (default) or `down` for a split. Omitted, it follows the user's terminal setting (a pane when `beside` names a pane). `beside` must be a terminal the same Mono opened and goes with `split`. `reveal` shows the terminal without moving the keyboard focus and without leaving the Mono's view; it defaults to true only when the project is the one in view, and then it never navigates: a dock terminal opens the dock, a pane is shown only when its tab is already the visible one, and a new tab is added to the tab strip without being selected (`revealed:false`). Only an explicit `reveal:true` may select another title tab (never another project); the keyboard then goes to the app's main view, never to the terminal, unless what had it is still on screen (the Mono's composer or details panel). It shows nothing for a project not in view, nor for a dock terminal while the user keeps terminals in the right panel. An idle terminal the same Mono opened with the same label is reused (`reused: true`) only when the shell itself holds it right now (asked of the PTY, not the one-second poll; when the system cannot tell, the last poll decides on macOS and Linux, while elsewhere, Windows included, a new terminal opens under the same label) and it stands in the folder asked for. A multi-line `command` for a new terminal is refused (see `send`).
  - **Typing.** `terminals.send {id,text?,key?}` types `text` and then presses `key`, which is one of `ctrl-c`, `enter`, `up`, `down`, `q`, `tab` or `esc`; give either or both, in one call the text is typed first. It runs at once and asks nobody: there is no approval dialog and no allow list (a Mono saved with an old `terminalAllow` list still loads, the list is ignored). The one rule is scope: the terminal must be one the same Mono opened, and its folder must be the project or inside it or one of its git worktrees. That is checked at write time, against the live folder of the process holding the terminal when the system can tell it (so a `cd` out of the project closes the terminal to the Mono) and else against the folder the terminal started in. The check is the same for text and for every key. Never typed into: a terminal that runs an agent CLI (asked of the PTY at the moment of the call), an exited terminal, a terminal the user opened. `text` is typed exactly as given and no Enter is added, so a Mono adds `key: "enter"` in the same call or the next to run it; `text` and `command` are at most 4096 bytes and take no control character except line breaks (control bytes only through `key`; error "use key for control keys"). Text with a line break is sent as one bracketed paste when the program in the terminal turned bracketed paste on; when it did not, the call is refused (a line break would run each line as it arrives). This rule is about what the terminal does with the text, not about permission, so it stays now that nothing asks the user.
  - **Stopping.** `terminals.stop {id}` sends Ctrl-C and, if the job that was in front is still in front 3 seconds later, hangs it up; it returns `{stopping:true}` at once. `terminals.close {id}` closes the terminal. `stop` and `close` only work on terminals the same Mono opened.
  - **Arranging.** `terminals.layout {preset,ids,reveal?,project?}` arranges 1 to 6 of the Mono's own terminals, wherever they are (dock tabs, title tabs or splits), into one title tab named `Logs <project name>` and returns `{tab,ids}`. `preset` is `columns` (side by side), `rows` (stacked) or `grid` (two columns, filled left to right; an odd last terminal spans the row); every part gets an equal share. Terminals in the dock leave it and become panes (a project needs a local session to host panes, else the call fails); panes in other tabs move in; the Mono's existing Logs tab for that project is reused and any of its panes not listed become title tabs of their own. It never moves the keyboard focus; `reveal` follows the rules of `terminals.open`. A pane the user drags out of its Logs tab stops being part of it.
  - **Marks and ownership.** Terminals a Mono opened show a small muted bot mark (accessibility label `Opened by Mono`) on the dock tab, the pane header and the title tab. A Mono's terminal pane borrows a local session of its project for its scope (never a cloud or remote one); when that session is deleted the pane moves to another local session of the project, or to the project's dock. State saved by an older version that still holds a Mono's dock tabs or panes (`mono_terminals`, or `mono`, `label`, `run` and `logs` in a pane) loads, and those terminals are dropped instead of reopening as the user's.
- `sessions.stop`, `sessions.archive` and `sessions.delete` take a `sessionId` to manage another session in the project. Monos can select an assigned project with `project`. Stop cancels the current turn and pauses queued messages; archive stops and saves the conversation for later restoration; delete stops and permanently removes the conversation. Open files, terminals and worktrees are kept. These actions cannot target the caller, Mono chats, habit runs or orchestration workers. A `sessions.delete` that targets one of those is refused and removes nothing. `sessions.delete` also takes `providerFiles: true`, for Monos and habit runs only (an Operator thread is refused), which removes the session's Claude Code or Codex session files from disk as well. This is irreversible: an agent should use it only for sessions the user clearly asked about. The call then waits and reports `providerFiles` as `removed` (something was removed from disk), `none` (nothing to remove, such as a harness with no cleanup) or `failed` with `problems`. `failed` means the session is deleted but some files may remain, because a removal failed or because files were kept on purpose, for example a Codex thread another conversation continues from. Without it the files stay and the result is `{"accepted":true}`. Deleting the last session of a folder removes that folder; an archived session keeps it. Reuse the same request ID when retrying a call: the stored result is returned and the cleanup does not run twice.
- `habits.add` and `habits.update` take a `schedule` with a `kind` of `hourly` (with `minute`), `daily`, `weekdays`, `weekly` (with `dayOfWeek`) or `interval`. An interval schedule runs every `hours` (a whole number from 1 to 24) from an anchor `time`: `{"kind":"interval","hours":4,"time":"09:00"}` runs at 09:00, 13:00, 17:00, 21:00, 01:00 and 05:00, carrying on across midnight. `time` is local 24-hour `HH:MM` and defaults to `00:00`. The sequence starts at `time` on the day the schedule is made (or changed), so a habit made before that time runs first at the anchor. When `hours` does not divide 24 the runs drift against the clock day by day, so the anchor time itself comes round only every lcm(`hours`, 24) hours. A run missed while Monoptah was closed runs at most once if it is under two hours late; there is never a backlog.
- `workflows.list` and `workflows.get` show a Mono's workflows, or one workflow with its steps, inputs, problems and last five runs. In the native app, a habit run can use only `workflows.list`, `workflows.get`, `workflows.runs` and `workflows.run`; the other `workflows.*` actions are for the Mono's own conversation. A heartbeat and a workflow's Ask-Mono question cannot use any of them. The Tauri app still refuses every `workflows.*` action from a habit run.
- `workflows.add` saves a workflow from a `workflow` object (name, description, inputs, inputValues, nodes, edges) or from `yaml` text in a workflow file. Either way it is always saved paused, however clean it is, and the result says so; the user enables it in the Workflows panel. When the result lists `issues`, its `note` says to fix them first with `workflows.update`. `workflows.update` replaces the definition of an existing workflow and keeps its id and run state. A session node's `harness` and `model` take exact ids from `models.list`, and `effort` one of that model's listed values; leave them out to use the Mono's own model. A node naming anything else is reported as a problem, so the workflow cannot run until it is fixed.
- `workflows.validate` takes the same input as `workflows.add` (a `workflow` object, or `yaml` with optional `values`) and runs the same parsing and checks without saving anything. It returns `issues`, plus the `commands` and `prompts` the steps would run, so they can be shown to the user before saving. It also lists an issue when the Mono is already at its limit of workflows, since `workflows.add` would be refused; pass the `id` of an existing workflow to check a change to it, which skips that limit. It also checks that every If condition and loop condition follows the condition grammar.
- `workflows.guide` takes no input and returns `{guide}`, the authoring guide in Markdown: the definition shape, every node type with its limits, templates and conditions, the output contract, the command safety rules, models, limits, the steps to follow with the user and worked examples. The guide is generated from the same constants the validator uses, and each example is checked by a test. Read it before adding or changing a workflow.
- `habits.export` returns a habit as a shareable `yaml` file (`kind: habit`, `version: 1`, name, schedule, instructions; nothing machine specific). `habits.import` saves a habit file given as `yaml`, disabled and marked as needing review: `habits.update` with `enabled: true` and `habits.run` refuse it until the user approves that version in the Habits panel. The result lists warnings for absolute paths and URLs in the instructions. A habit run can use `habits.list` and `habits.export` but not `habits.import`.
- `workflows.import` saves a workflow file given as `yaml` (with optional `values` for its inputs), paused. A workflow made from a file (`workflows.import`, or `workflows.add` with `yaml`) is marked as needing review: `workflows.resume`, `workflows.run`, `workflows.resumeRun` and `workflows.update` with `enabled: true` refuse it until the user approves that version in the Workflows panel.
- `workflows.export` returns a workflow as a shareable file, and refuses one that contains an absolute path.
- `workflows.setInputs` sets the values of a workflow's declared inputs; a project input takes a path.
- `workflows.run` starts a run now (it refuses a paused workflow), `workflows.stop` ends the run in progress, and `workflows.runs` lists a workflow's recent runs with each step's status per branch.
- `workflows.pause` and `workflows.resume` turn a workflow's trigger off and on. `workflows.resumeRun` continues an interrupted run from where it stopped.
- `workflows.remove` deletes a workflow and its run history; it refuses while the workflow is running.
- Command steps run shell commands in a project on macOS and Linux; on Windows they are not supported yet and fail when reached.
- When a Mono successfully stops, archives or deletes a session it is monitoring, its pending completion report for that session is dismissed, including any queued report. The Mono confirms the action in its current reply. Reports for other sessions and other Monos are kept. Rejected launches or follow-ups return a CLI error without a later completion report.
- `notes.list` returns titles and short previews; `notes.read` returns one full note by ID.
- `notes.list` accepts `limit` and `offset`. `notes.write` creates a note from its
  `body`, with optional title and tags; pass an existing note `id` to update just
  its title, body or tags while preserving the other fields.

Retry an uncertain mutation with the same request ID and identical input.
Unknown fields and invalid options produce errors instead of being ignored.

## Orchestration workers

Orchestration workers keep their existing scoped `control` workflow and do not receive this app access.

Return to the [README](../README.md) for a quick start.
