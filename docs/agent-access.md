# Agent access with /operator

## Enable access

Type `/operator` at the start of a composer message to enable Monoptah access in that thread. For example, `/operator start two Codex sessions: one to inspect the API and one to review the UI`, or `/operator list my notes`. The slash picker also offers this command. The transcript shows only the request text in a translucent amber bubble; Monoptah removes the command from the request sent to the agent and supplies the local `app` CLI path and instructions on that turn. Later turns in the same thread can use the CLI without repeating `/operator`; other threads receive no CLI instructions or app access. The CLI can act only during an active agent turn. The agent can run the shown `app --help` command for the exact JSON input fields.

## CLI actions

- `models.list` shows available providers, models, settings, and permission modes.
- `sessions.start` opens a tab in the current project with a prompt. Set `placement: "right"` or `placement: "down"` to split the calling session's pane instead; `besideSessionId` selects another visible session pane in the project. Reuse the returned session ID as the next `besideSessionId` to build nested layouts. By default it submits the prompt; set `draft: true` to save it unsent without starting an agent turn. It accepts a provider, model, effort or other model settings, permission mode, and current checkout or new worktree choice. Set `worktreeCwd` to a path from `worktrees.list` for a specific existing checkout. Use `worktrees.create` to create a worktree on a named new or existing local branch, then pass its path as `worktreeCwd`. Omit `runtimeMode` to inherit the calling session's permission mode, or set it explicitly to override. It returns the new session ID as soon as the pane and prompt are accepted, so the agent can move it into a folder immediately.
- `sessions.start` and `sessions.send` accept `completionDelivery: "group" | "each"` (default `"group"`). With `"each"`, the session's completion report reaches the calling Mono as soon as that session stops, without waiting for the Mono's turn or sibling sessions, as a new turn once the Mono is idle (several may queue while it is busy). Habit runs always use `"each"`: sessions a habit run starts report to the Mono's chat, not to the run, and the report still arrives after the run has ended. The field is ignored when the launch is not monitored (a draft, or `notifyOnComplete: false`).
- `sessions.start` accepts `parentSessionId` from a Mono or its habit runs. The new session is nested under that parent in the sidebar and its ID becomes `app-<parentSessionId>-<requestId>`. The parent must be a session that Mono (or its habit runs) started in the same project during the current app run; the record is kept in memory and lost on restart. Nesting is one level deep, so a child cannot be a parent. IDs over 255 characters are rejected, so use a short request ID. The completion report still goes to the Mono, and the child gets no app access.
- `sessions.start` accepts `folderName` (up to 100 characters) and `folderId` to file the new session in a folder. An existing `folderId` wins and the folder is never renamed. An unknown `folderId` with a `folderName` creates a new folder; an unknown `folderId` alone fails with "Folder was not found in this project". A `folderName` alone always creates a new folder, even if one with that name exists. New folders use the Mono's color, and the result includes `folderId` and `folderName`. Without these fields the session goes in the Mono's default folder when **Group in a folder** is on for that Mono.
- `parentSessionId`, `folderName` and `folderId` do not override a Mono's hidden-launches setting. For them to show, turn on **Show sessions in sidebar** for that Mono; nesting is only drawn in the inset sidebar layout. Use request IDs without hyphens with `parentSessionId` so the sidebar cannot mistake another session's ID for the parent.
- `sessions.list` shows project sessions and their archived status. `sessions.read` returns up to three recent user/assistant exchanges, with a cursor for older exchanges and a per-message character cap. `sessions.send` submits a follow-up to an idle session, while `sessions.draft` saves an unsent message for the user to review. `folders.list` and `folders.move` organize project sessions in sidebar folders, including a new folder.
- `sessions.stop`, `sessions.archive` and `sessions.delete` take a `sessionId` to manage another session in the project. Monos can select an assigned project with `project`. Stop cancels the current turn and pauses queued messages; archive stops and saves the conversation for later restoration; delete stops and permanently removes the conversation. Open files, terminals and worktrees are kept. These actions cannot target the caller, Mono chats, habit runs or orchestration workers. Reuse the same request ID when retrying a call.
- `habits.add` and `habits.update` take a `schedule` with a `kind` of `hourly` (with `minute`), `daily`, `weekdays`, `weekly` (with `dayOfWeek`) or `interval`. An interval schedule runs every `hours` (a whole number from 1 to 24) from an anchor `time`: `{"kind":"interval","hours":4,"time":"09:00"}` runs at 09:00, 13:00, 17:00, 21:00, 01:00 and 05:00, carrying on across midnight. `time` is local 24-hour `HH:MM` and defaults to `00:00`. The sequence starts at `time` on the day the schedule is made (or changed), so a habit made before that time runs first at the anchor. When `hours` does not divide 24 the runs drift against the clock day by day, so the anchor time itself comes round only every lcm(`hours`, 24) hours. A run missed while Monoptah was closed runs at most once if it is under two hours late; there is never a backlog.
- `workflows.list` and `workflows.get` show a Mono's workflows, or one workflow with its steps, inputs, problems and last five runs. Only a Mono's own conversation can use the `workflows.*` actions.
- `workflows.add` saves a workflow from a `workflow` object (name, description, inputs, inputValues, nodes, edges), enabled once it has no problems, or from `yaml` text in a workflow file, which is saved paused. `workflows.update` replaces the definition of an existing workflow and keeps its id and run state.
- `workflows.import` saves a workflow file given as `yaml` (with optional `values` for its inputs), paused. A workflow made from a file (`workflows.import`, or `workflows.add` with `yaml`) is marked as needing review: `workflows.resume`, `workflows.run` and `workflows.update` with `enabled: true` refuse it until the user enables or runs it in the Workflows panel.
- `workflows.export` returns a workflow as a shareable file, and refuses one that contains an absolute path.
- `workflows.setInputs` sets the values of a workflow's declared inputs; a project input takes a path.
- `workflows.run` starts a run now, `workflows.stop` ends the run in progress, and `workflows.runs` lists a workflow's recent runs with each step's status per branch.
- `workflows.pause` and `workflows.resume` turn a workflow's trigger off and on. `workflows.resumeRun` continues an interrupted run from where it stopped.
- `workflows.remove` deletes a workflow and its run history; it refuses while the workflow is running.
- Command steps run shell commands in a project on macOS and Linux; on Windows they are not supported yet and fail when reached.
- When a Mono successfully stops, archives or deletes a session it is monitoring, its pending completion report for that session is dismissed, including any queued report. The Mono confirms the action in its current reply. Reports for other sessions and other Monos are kept. Rejected launches or follow-ups return a CLI error without a later completion report.
- `notes.list` returns titles and short previews; `notes.read` returns one full note by ID.

## Orchestration workers

Orchestration workers keep their existing scoped `control` workflow and do not receive this app access.
