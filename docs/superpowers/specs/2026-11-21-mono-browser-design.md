# Mono Browser (real Chrome via Playwright MCP extension mode) - design

Status: spec, not scheduled. Native app only.
Source: research session 2026-11-21. Extension mode was proven manually on macOS; Monoptah Native
needed Full Disk Access to read `~/Library/Application Support/Google/Chrome`.

## Goal

A per-Mono setting that lets a Mono drive the user's real Chrome (a chosen profile, logged-in
sessions) through Microsoft Playwright MCP in extension mode
(`npx @playwright/mcp@latest --extension`, extension "Playwright MCP Bridge",
id `mmlmfjhmonkocbjadbfplnigmagldckm`). It must work for both the Claude Code and Codex
harnesses and must never touch the user's global MCP config.

## Non-goals (v1)

- Silent extension install (Chrome does not allow it).
- Browsers other than Chrome stable. Linux and Windows profile discovery (paths differ; later).
- Headless or separate-profile automation (use plain Playwright MCP for that).

## Research findings

Versions examined: `@playwright/mcp` 0.0.86, `playwright-core` 1.66.0-alpha-2026-11-18 (the
extension logic lives in core `lib/coreBundle.js`), extension source
`microsoft/playwright/packages/extension/src`.

### Profile targeting (supported natively)

- `--profile-dir-name <dir>` or `PLAYWRIGHT_MCP_PROFILE_DIR_NAME` selects the profile directory
  (for example `Profile 6`).
- Without it, `findPlaywrightExtensionProfile` picks statically from disk: `profile.last_used`
  first, then `Default` and `Profile N` in number order, and takes the first profile with
  `Extensions/<id>` or an entry in `Preferences`/`Secure Preferences` `extensions.settings`.
  This is unpredictable, so the app always passes the profile explicitly.
- Other knobs: `--user-data-dir` / `PLAYWRIGHT_MCP_USER_DATA_DIR` (leave unset for the real
  Chrome), `--executable-path` / `PLAYWRIGHT_MCP_EXECUTABLE_PATH`, `--browser` (default `chrome`),
  `--background` (open without stealing focus).
- Launch: the server spawns the Chrome binary with `--profile-directory=<dir>` and
  `chrome-extension://<id>/connect.html?mcpRelayUrl=ws://127.0.0.1:<port>/extension/<uuid>&token=...`.
  A running Chrome hands the URL to the existing instance, which opens it in that profile.

### Relay and several open profiles

- Each run starts its own WebSocket relay on a random port with a per-run uuid path. It accepts
  exactly one extension connection and one CDP client; a second extension is rejected.
- With three profiles open and the extension installed in all of them, only the profile that
  received the connect URL (the `--profile-directory` one) connects. The others never learn the
  URL. There is no "first to connect wins".
- With a token the connect page connects automatically (30 s timeout, then a clear error).
  Without a token it shows a tab picker and waits forever, which is unusable for a Mono.

### Token scope

- Generated by the extension (`crypto.getRandomValues`), stored in the extension's
  `localStorage` key `auth-token`, so it is **per Chrome profile** (per install in that profile).
- One token does not work for another profile: the extension compares it with its own value and
  shows "Invalid token provided.".
- It can be regenerated ("Rotate token" on the extension's `manage.html`). The old token stops
  working for new connections; existing connections stay.
- So the stored pair is always (profile dir, token of that profile).

## User-facing behaviour

Settings for one Mono gain a **Browser** tab next to General, Soul, Memory, Emoji.

1. **Enable** toggle (off by default).
2. **Prerequisites**, each with a status and a fix action:
   - Chrome installed (`/Applications/Google Chrome.app` or the Playwright registry lookup).
   - Full Disk Access: try to read `~/Library/Application Support/Google/Chrome/Local State`; on
     `EPERM` show a button that opens System Settings > Privacy > Full Disk Access.
   - `node`/`npx` on the GUI PATH (same resolution as provider launch, `apply_gui_env`).
3. **Profile picker** from `Local State` `profile.info_cache`: name, email (`user_name`), avatar.
   Warn (do not block) when another Mono already uses the same profile: one relay per run means
   two Monos would fight over the same browser.
4. **Install extension**: open Chrome with `--profile-directory=<dir>` at the Web Store page of
   the extension. Poll `<profile>/Extensions/<id>` (and `Secure Preferences`
   `extensions.settings.<id>`) until present, then show "Installed".
5. **Token**: button opens `chrome-extension://<id>/manage.html` in that profile; the user copies
   the token and pastes it. Stored encrypted (see Storage). Changing the profile clears the token.
6. **Test connection**: start the MCP server with the per-Mono config, call `browser_tabs`
   (list), report success or the server error (wrong token, timeout, extension missing).
7. **Safety rules**:
   - Blocked origins, prefilled with banks, e-wallets and payment pages (editable list).
   - Allowed origins (optional; when set, only these).
   - "Ask before send, post, delete or pay" (on by default).
   - Read-only by default: the Mono only reads unless the user's request asks for an action.

## Storage

- Non-secret fields go on `Mono` (serde default, so old rosters load):
  `browser: Option<MonoBrowser { enabled, profile_dir, profile_name, blocked_origins,
  allowed_origins, confirm_actions }>` in `crates/monocode-core/src/mono.rs:47`, persisted with
  the roster JSON (`Roster::load` `mono.rs:328`, `save` `mono.rs:352`). That JSON is plaintext,
  so the token never goes there.
- The token reuses the existing at-rest encryption, not Keychain:
  `crates/monocode-core/src/accounts/sealed.rs` (AES-256-GCM, 32-byte `credentials.key` next to
  the store database, `seal` :134, `open` :151, fresh 12-byte nonce per seal). Follow the
  `git_credentials.rs` pattern (table :42, AAD :270, seal :355, open :474):
  - New table `mono_secrets(mono_id TEXT, name TEXT, nonce BLOB, ciphertext BLOB,
    created_at INTEGER, PRIMARY KEY(mono_id, name))`, `CREATE TABLE IF NOT EXISTS`.
  - AAD `b"mono-secret\0" + mono_id + "\0" + name`, name `playwright-extension-token`.
  - Core functions `set_mono_secret`, `mono_secret`, `delete_mono_secret` (the sealed API is
    `pub(crate)`). Deleting a Mono deletes its secrets.
  - Protection level: the key file sits beside the DB, so this is obfuscation against casual
    reads and backups of the DB alone. Accepted by the user.

## Runtime

Built in `crates/monocode-core/src/provider.rs` (launch starts about :1461), only when the Mono's
browser is enabled, the token decrypts and prerequisites passed at last check.

Server definition (`playwright_browser`):

- command `npx`, args `["-y", "@playwright/mcp@<pinned>", "--extension", "--background"]`.
  Pin the version the app was tested with instead of `@latest`; bump deliberately.
- env: `PLAYWRIGHT_MCP_PROFILE_DIR_NAME=<dir>`, `PLAYWRIGHT_MCP_EXTENSION_TOKEN=<token>`,
  `PLAYWRIGHT_MCP_BLOCKED_ORIGINS` / `PLAYWRIGHT_MCP_ALLOWED_ORIGINS` (`;`-separated, check
  the exact names against the pinned version), and `--output-dir` set to a per-Mono folder for
  snapshots and screenshots.
- The token never goes into argv (visible in `ps`). Set it on the provider process env and let
  the MCP config reference it:
  - **Claude Code**: add the server to the existing `servers` map passed as one
    `--mcp-config '{"mcpServers":{...}}'` (`provider.rs:1552`), with
    `"env": {"PLAYWRIGHT_MCP_EXTENSION_TOKEN": "${PLAYWRIGHT_MCP_EXTENSION_TOKEN}", ...}`
    (Claude expands `${VAR}`). Add `mcp__playwright_browser` to `--allowedTools`
    (`provider.rs:1555`) only for read tools; action tools stay on the normal permission prompt
    when "ask before" is on. Do not add `--strict-mcp-config`: normal sessions do not use it today
    and it would drop the user's own servers. Name the server `playwright_browser` so it does not
    collide with a user-level `playwright` server.
  - **Codex**: same as `mono::bridge::configure_codex` (`crates/monocode-core/src/mono/bridge.rs:367`)
    and `visual_bridge::configure_codex` (`visual_bridge.rs:732`): `-c` overrides
    `mcp_servers.playwright_browser.command`, `.args`, `.env_vars=["PLAYWRIGHT_MCP_EXTENSION_TOKEN", ...]`
    (forward from the parent env instead of an inline `env` table, which would put the token in
    argv). Nothing is written to the user's `config.toml`; Monos already run with their own
    `CODEX_HOME` (`provider.rs:1473-1482`).
- Startup: `npx` can be slow on first run; Claude waits `MCP_TIMEOUT` (30 s default). Consider
  warming the npx cache during Test connection.

## Prompt context

Append a browser block to `mono::instructions` (`crates/monocode-core/src/mono.rs:434`), which
reaches Claude through `--append-system-prompt` (`provider.rs:1537`) and Codex through
`developerInstructions` (`provider.rs:555-560`). It is hashed into the `mono-context:{id}` receipt
(`crates/monocode-gpui/src/runtime.rs:511-514`), so a rule change is detected. Content:

- A real Chrome is available through `playwright_browser`, profile "<name>" (the user's own
  logged-in browser).
- Read-only by default; ask before sending, posting, deleting, buying or changing settings.
- Never open blocked origins; when allowed origins are set, stay inside them.
- Save snapshots to a file in the output dir and search or filter them instead of reading a full
  snapshot into context.
- Do not close the user's tabs you did not open.

## UI injection points

- Per-Mono settings panel: `SettingsSection` in `crates/monocode-gpui/src/monos/panels.rs:22`,
  dispatch :1679, tab list :1764 (add `Browser`), model after `general_settings` :1880.
- Global page Settings > Monos (`crates/monocode-gpui/src/settings/pages/monos.rs:44`) can show a
  read-only overview of which Mono uses which profile.

## Audit

Per Mono, append-only log (store table `mono_browser_audit(mono_id, session_id, ts, tool, url,
summary)`) fed from tool-call events of `playwright_browser` in the session stream: tool name,
target URL, short action (click, type with the value masked, navigate). Shown in the Browser tab
as the last N entries.

## Risks and mitigations

- Origin rules are enforced by the MCP server, not by Chrome; a Mono with `browser_run_code_unsafe`
  could step around them. Mitigation: do not allow that tool (deny it via `--allowedTools`
  absence plus prompt rule; for Codex check `disabled_tools`/`enabled_tools` support).
- Two Monos on one profile: warned in UI; the second run's connect page opens a second relay,
  both can drive tabs. Acceptable with the warning.
- Token rotated in Chrome: Test connection and the runtime error say "Invalid token", the tab
  shows "Token needs update".
- Full Disk Access revoked: prerequisite check fails, the server is not injected, the prompt
  block is omitted.
- `@playwright/mcp` flag names change between versions: pin the version.

## Implementation notes

Status: implemented for the native app. Code: `crates/monocode-core/src/mono/browser.rs`
(setting, token store, audit, MCP config, prompt block, probe), `crates/monocode-gpui/src/monos/browser_ui.rs`
(the Browser tab), launch wiring in `provider.rs` and `runtime.rs`.

### Open questions, verified on `@playwright/mcp` 0.0.86 (`playwright-core` 1.66.0-alpha-2026-11-18)

Read from the published packages (`npm pack`, files only read, nothing executed).

- Origin and output env names exist exactly as guessed: `PLAYWRIGHT_MCP_BLOCKED_ORIGINS`,
  `PLAYWRIGHT_MCP_ALLOWED_ORIGINS` (both `;`-separated), `PLAYWRIGHT_MCP_OUTPUT_DIR`,
  `PLAYWRIGHT_MCP_PROFILE_DIR_NAME`. The matching flags are `--blocked-origins`, `--allowed-origins`,
  `--output-dir`, `--profile-dir-name`. The app uses the flags (not secret, same on both harnesses).
- The token has no flag: it is read only from `process.env.PLAYWRIGHT_MCP_EXTENSION_TOKEN`
  (`CDPRelayServer` constructor). So the token can only travel in the environment.
- Origin matching: an entry is turned into the glob `<origin>/**` (`originOrHostGlob`); a wildcard
  such as `*.example.com` is not valid, subdomains are listed one by one. Blocked routes are
  registered per browser context; an allow-list adds a catch-all `**` abort first. The server's own
  help says both lists are not a security boundary and do not affect redirects.
- No tool allow/deny option exists in the server (no `--exclude-tools`). Optional capabilities
  (`network`, `storage`, `devtools`, `pdf`, `vision`, `testing`) are off unless `--caps` is given, and the
  app never passes it. Tools that matter for the rules: `browser_run_code_unsafe` (arbitrary
  code, "RCE-equivalent"), and `browser_route` / `browser_unroute` (network capability). A route added
  later outranks the origin routes, so these three are denied explicitly (`BLOCKED_TOOLS`).
- Files: a plain `filename` of a snapshot or screenshot resolves against `--output-dir`, and the
  output dir is an allowed root, so "save the snapshot to a file by name" works without extra flags.
- Codex `env_vars`: a name in `mcp_servers.<name>.env_vars` (source `local`, the default) is copied
  from the Codex process environment into the MCP server's environment (`create_env_for_mcp_server`
  in `rmcp-client`), next to PATH and HOME. This is what the existing `monocode_app` entry relies on,
  so the app sets the token on the Codex app-server process and names it in `env_vars`. Codex also
  supports `disabled_tools` and `startup_timeout_sec` per server, both used.
- Claude: `${VAR}` in a server `env` map is expanded from the Claude process environment
  (the CLI has a "Missing environment variables" error for it), `--disallowedTools` exists, and
  `--strict-mcp-config` is not passed.

### Deviations and decisions

- Pin: `@playwright/mcp@0.0.86` (`PLAYWRIGHT_MCP_VERSION`). It is current `latest`. Bump with the
  flags re-read from the new version.
- Origin rules and the output folder use the verified flags in argv instead of env entries. Only
  the token is an env reference. `--profile-dir-name` is always passed.
- Denied tools: `browser_run_code_unsafe`, `browser_route`, `browser_unroute`, `browser_evaluate`. Claude gets
  `--disallowedTools mcp__playwright_browser__<tool>`; Codex gets `disabled_tools`. The origin
  rules stay best effort (redirects), as the server says.
- Claude `--allowedTools` for the server holds only read tools (`browser_snapshot`,
  `browser_take_screenshot`, `browser_console_messages`, `browser_network_requests`, `browser_find`,
  `browser_wait_for`) while "ask before" is on, and the whole server when it is off. Codex uses `default_tools_approval_mode` `writes` while "ask before" is on and `approve` when it is off.
- Residual risk: the token is in the provider process environment. That hides it from argv only;
  other processes of the same user can read an environment (for example `ps eww`), and a shell
  tool the Mono runs inherits it. Codex drops variables with TOKEN in the name from its shell tool
  by default; Claude's Bash tool does not. I looked for a Claude setting that scrubs the
  environment of its Bash tool and found none that is verified for an arbitrary variable
  (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` exists but forces the default permission mode, so it is not
  used). The prompt forbids printing or revealing environment variables, credentials and tokens,
  and running `env` or `printenv`.
- "Ask before" and Claude's permission modes: only `default`, `plan` and `acceptEdits` prompt for
  an MCP tool (`acceptEdits` is described by the CLI as "ask before file changes", so it
  auto-accepts file edits only). `auto` (a classifier approves without asking, and the default
  access for Monos) and `bypassPermissions` never ask, so `--allowedTools` cannot make a tool wait.
  With "ask before" on and any mode other than those three (`claude_mode_prompts`), the
  page-changing tools (`WRITE_TOOLS`: click, type, fill_form, select_option, press_key,
  press_sequentially, drag, drop, file_upload, handle_dialog, check and the mouse tools) are added
  to `--disallowedTools`, so only reading and navigating remain; the Browser tab says so. A user
  who wants those tools under Auto turns "ask before" off or uses Supervised or Auto-accept edits.
  No PreToolUse hook was relied on because I could not verify that a hook can force a prompt in
  these modes. In the prompting modes the tools take the normal permission prompt.
- Codex: `default_tools_approval_mode = "writes"` makes every tool not marked read-only wait for
  approval (codex-rs `core/src/mcp_tool_call.rs`, `requires_mcp_tool_approval_for_mode`). When the
  approval policy is `never` (Full Access, read-only) such a call is denied: the approval step in
  the same file returns a `ReviewDecision::denied("MCP tool call requires approval, but approval
  policy is never")` when `approval_policy == AskForApproval::Never`, so it does not run. Auto
  (`on-request`) and Supervised prompt normally. With "ask before" off the mode is `approve`.
- `browser_evaluate` is also denied on both providers: page JavaScript can reach origins the rules
  block. The denied set is `browser_run_code_unsafe`, `browser_route`, `browser_unroute`,
  `browser_evaluate`.
- The browser server is resolved once per launch (`run_operation`), and both Claude and Codex get
  the rules text that matches it (`Settings.browser_available`). The profile name is reduced to
  letters, digits and a few punctuation marks before it goes into the rules.
- The setting has a `ready` flag, kept true to the last check by the Browser tab (prerequisites, a
  profile and a saved token). A launch also re-checks Chrome and read access to `Local State`
  right before adding the server, and decrypts the token. If any fails the server is not added and
  the browser paragraph is left out of the rules for that launch (`launch_instructions`). The
  `mono-context` receipt hash uses the stored setting, so a failure at launch does not change it.
- Install detection is the folder `Extensions/<id>` or an `extensions.settings.<id>` entry in
  `Secure Preferences` / `Preferences`; a disabled extension still counts as installed.
- Test connection spawns the pinned server like a launch does (`npx`, token in env), sends
  `initialize` and `tools/call browser_tabs {action: list}`, and maps "Invalid token" to
  "Token needs update". The tab polls every 2 seconds for the install while it is open.
- The audit records a call once, when it finishes, from the tool name (Claude
  `mcp__playwright_browser__*`, Codex `playwright_browser:*`). It keeps tool, URL argument and a
  short action; typed text, form values and selected options are never stored. The URL is only known
  for tools that take one (navigate).
- Not done: the read-only overview under Settings > Monos, Linux and Windows profile discovery
  beyond default paths, and warming the npx cache.
